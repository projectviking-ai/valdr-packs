# CLI starters, discovery, and executable actions

The shipped adapters are deliberately useful starter sets. Extend only the commands a user needs; full-tree discovery is optional unless the task explicitly requests it. Users maintain and test their own extensions. Keep full inventories out of executable manifests, and never equate inventory coverage with execution support.

Record the installed executable/version before discovering commands. Use native metadata
or help without installing plugins, logging in, switching profiles, or executing leaf actions.
The supplied `scripts/discover-cli.mjs` helper emits inventory/coverage evidence;
read its `--help` for current arguments. Evidence lives outside the executable pack under
a local directory outside the pack, so discovery changes do not change installed pins. Keep host-specific captures private; review executable fingerprints, platform details, components, and user aliases before sharing an inventory.

Inventory each command's path, aliases, group/leaf role, metadata source and schema confidence.
Record plugin/component scope, discovery failures and unvisited paths. A full tree means
all commands in the stated installed scope are accounted for; it does not mean all can execute.
If native introspection fails, label a filesystem/model fallback and its gaps rather than
calling the result complete. Missing runtimes and auth are INCOMPLETE, not passing skips.

## Native sources

- `gh help reference` supplies built-in command paths and aliases. User aliases, extensions
  and dynamically added preview commands need separate declared scope; never execute aliases
  just to learn what they do.
- AWS CLI's installed service models enumerate modeled API operations. Account for high-level
  commands, customizations, waiters and paginators separately; a botocore operation list alone
  is not the complete CLI tree. Do not call APIs during discovery.
- `gcloud meta list-commands --hidden` and native CLI-tree metadata describe installed surfaces.
  Components and alpha/beta availability vary. An import failure is a real coverage gap.
- `acli` exposes groups through native `--help`; recursively ask each discovered path for
  help. Distinguish group nodes from executable leaves and retain command aliases.

## Action mapping

Keep a deterministic command-path-to-action-ID mapping. For example, `jira workitem view`
can map to `jira-workitem-view`. Detect collisions before writing; do not silently rename
existing IDs when a CLI adds a command. Preserve exact catalog paths and alias information.

Every discovered leaf gets an executable action or an explicit unsupported coverage entry.
When exposing that tree in the Builder, materialize unsupported leaves as manifest actions:

```yaml
id: auth-login
path: [auth, login]
name: auth login
description: Interactive host authentication.
inputSchema:
  type: object
  properties: {}
  additionalProperties: false
outputSchema: true
execution: unsupported
unsupportedReason: Authentication remains a host setup task; no unattended action contract.
sideEffects: unknown
retry: manual
```

An inventory record alone is not a Builder action. The starter pack exposes a bounded set
of typed read actions; it does not populate the Builder with every unsupported CLI command.
Use the inventory to extend a tool deliberately. Interactive prompts, streaming sessions,
install/login/config mutation, arbitrary shell/argv passthrough and unverified writes stay
unsupported until an explicit action contract and its failure/retry behavior are implemented.

For supported actions, verify accepted flags with native help and input/output fixtures.
Use a stub CLI for deterministic argv/error tests, real installed version/help for local
compatibility, and a separately authorized read/write for authenticated behavior. Report
these evidence levels separately. A JSON pass-through output schema does not guarantee
stable fields for workflow mappings.

The source generator `scripts/generate-user-workflow-cli-tools.mjs` emits four independent
`tools/<cli>/<cli>.tool.yaml` and `tools/<cli>/runner.mjs` pairs for `gh`, `aws`, `gcloud` and
`acli`. A tool snapshot contains only its own CLI command table and environment names.
Edit the source generator, then run `bun scripts/generate-user-workflow-cli-tools.mjs`;
its `--check` mode verifies both generated manifests and runners. Preserve local edits before
regenerating, and bump each tool whose generated bytes or manifest change. A change to one
CLI does not require rebuilding the others' identities.
Keep the captured old inventory when comparing a new CLI version, and report
added/removed/changed command paths.
