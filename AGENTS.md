# Repository guidance

This repository contains distributable Valdr agent packs, skills, and packaging scripts. It is the source for pack content; Valdr's application/runtime code lives elsewhere. Keep work scoped to this repository and use the installed or released Valdr CLI.

## Sources and layout

- `skills/`: canonical skill folders, each with a `SKILL.md` entrypoint. Operator skills are thin wrappers that load live personas and capabilities; avoid duplicating those instructions here.
- `valdr-packs/valdr/`: layered agent-pack sources. Raider uses `shared + raider`; Vanguard adds `vanguard`; Sovereign adds `sovereign`. Later layers override matching relative paths. The tier builder generates the concrete `pack.yaml`.
- `valdr-packs/valdr-workflow/`: independently versioned Workflow pack, including workflow definitions and workflow-owned agents.
- `valdr-packs/valdr-tools/`: standalone user-tool manifests, runners, and fixtures.
- `scripts/`: packaging, generation, validation, and Node test tooling. Shared build logic lives in `scripts/lib/`.
- `build/`: generated staging trees and archives; do not edit or commit these outputs.

Read the relevant directory README and the format specifications before changing pack content:

- [PACK-SPEC.md](valdr-packs/PACK-SPEC.md): manifests, discovery, and tool inventories.
- [AGENT-SPEC.md](valdr-packs/AGENT-SPEC.md): agent manifests and capability bindings.
- [PROMPT-SPEC.md](valdr-packs/PROMPT-SPEC.md): tagged prompt Markdown.
- [Layered pack guide](valdr-packs/valdr/README.md): tier composition and overrides.
- [Workflow guide](valdr-packs/valdr-workflow/README.md) and [Tools guide](valdr-packs/valdr-tools/README.md): their respective contracts and validation.

Some specification examples use older directory layouts. Resolve paths against the current tree and use the Makefile and CI workflows for current commands.

## Authoring rules

- Preserve tier boundaries: Raider is manual/UI guidance; Vanguard adds PM MCP without live session orchestration; Sovereign adds sessions. Put content in `shared/` only when appropriate for every tier.
- All three tiers import as logical pack `valdr`. Preserve shared handles, `valdr.*` capability keys, and relative paths when adding overrides.
- Concrete pack manifests discover content through `includes`. Ensure new files are reachable through those paths; do not add redundant lists of every agent or capability.
- Agent manifests conventionally use `<handle>.agent.yaml`, live beside their content, and require exactly one `core` capability. Pack identity/version belongs in `pack.yaml`, not individual agent manifests.
- Preserve capability/prompt discovery headers and keep their IDs, pack names, roles, and categories consistent with YAML bindings. Keep detailed guidance hot-loaded where the surrounding agents follow that pattern.
- Use fully qualified MCP tool names in skill examples. Update the skill index when adding or removing an entry.
- For user-tool changes, read [the authoring skill](skills/valdr-workflow-tools/SKILL.md) and its contract references. Keep explicit file inventories, typed inputs/outputs, bounded execution, and accurate effects/retry declarations. Changed tool content requires a new revision.
- CLI adapter manifests and runners for `gh`, `aws`, `gcloud`, and `acli` are generated by `scripts/generate-user-workflow-cli-tools.mjs`. Change the generator, regenerate with Bun, and review the emitted diff; do not maintain generated files independently.
- When changing workflows, check exact subworkflow version references and related agent/prompt contracts. Source validation must report no unresolved workflow references before release.

## Validation and builds

Run commands from the repository root. CI uses Node.js 22 and Bun; there is no root package-manager install step. GNU Make drives the normal checks.

| Change or purpose | Command |
| --- | --- |
| Layered packs and shared script checks | `make ci-validate` |
| Layered packs only | `make validate-valdr-pack` |
| Script tests and generated CLI-tool freshness | `make test-scripts` |
| Workflow and Tools pack validation | `make validate-valdr-workflow validate-user-workflow-tools` |
| Full user-tool protocol/archive tests | `make test-user-workflow-tools` |
| Planning-team workflow regression checks | `node --test scripts/planning-team-workflow.test.mjs` |
| Generated CLI adapters only | `bun scripts/generate-user-workflow-cli-tools.mjs --check` |
| Build all five release archives | `make build-valdr-all` |

`make ci-validate` does not include the separate Workflow/Tools CLI validation targets. Run those when touching either pack. The full user-tool tests also require Python 3, POSIX `sh`, `jq`, and Go; see the Tools guide.

`VALDR_BIN` defaults to `valdr` on `PATH`; override it with `make VALDR_BIN=/absolute/path/to/valdr <target>` when needed. Workflow validation/builds enforce the version in `VALDR_WORKFLOW_CLI_VERSION`. Read that file rather than hardcoding a CLI version. A local pack check does not prove successful live import or workflow execution; report the validation actually performed.

For documentation-only changes, check referenced paths, command accuracy, and `git diff --check`; a full archive build is unnecessary.

## Versions, installation, and publication

- Root `VERSION` is the pack-set release version; scripts read it through `scripts/lib/version.mjs`. Standalone manifests, workflow definitions, and tools also carry their own versions/revisions. Do not treat the CLI pin, pack-set version, and entity versions as interchangeable or bump them as incidental cleanup.
- `make sync-skills` replaces project-local `valdr-*` skill copies. Global sync targets, including `make sync-all`, replace installed `valdr-*` skills under the user's home directory. Edit `skills/` first and sync only when installation is requested.
- `.github/workflows/release.yml` publishes five archives on matching changes pushed to `main`. Treat pushes/merges to `main` as potential publication actions and obtain authorization before releasing.
- Inspect `git status` before editing and preserve unrelated staged, unstaged, and untracked work. Obtain approval for the exact staged paths and commit message before committing, pushing, or opening a PR.
- **The `gh` CLI requires elevated privileges and must execute outside the sandbox, including read-only commands.** Use the tool's escalation mechanism when invoking it.

## Superpowers documents

**Place all Superpowers-generated documents under the repository-root `.superpowers/` directory.** This includes brainstorming/design notes, specifications, implementation plans, reviews, and other working documents. Use subdirectories such as `.superpowers/specs/` and `.superpowers/plans/`; this overrides skill defaults such as `docs/superpowers/`.

`.superpowers/` is ignored by Git. Keep it ignored and never stage or commit its contents. Maintain requested repository documentation in its appropriate source location; the `.superpowers/` rule applies to Superpowers working documents.

## Assistant plugin packaging

- Both marketplace catalogs point to `./plugins/valdr`; keep that generated package limited to the seven public skill folders, their resources, the user installation README, license text, and the Codex/Claude manifests. Do not add checkout configuration, development skills, scripts, test output, or private environment files to that directory.
- Plugin versions live in `plugins/valdr/.codex-plugin/plugin.json` and `plugins/valdr/.claude-plugin/plugin.json`, independently of pack-set `VERSION`. Keep them aligned and bump both when publishing changed plugin content. Run `node scripts/sync-plugin.mjs` after changing public skills. Generated Codex starter prompts qualify skill mentions with the plugin namespace; standalone source metadata keeps its unqualified names. CI checks for drift with `node scripts/sync-plugin.mjs --check`. Test local installs from this package boundary.
- `make sync-skills` remains available for project-local developer setup. It copies the public source skills into local assistant directories.
- Maintain shipped CLI adapter sources through `scripts/generate-user-workflow-cli-tools.mjs`, regenerate with Bun, and bump changed tool revisions. The public discovery helper accepts the manifest to compare explicitly and must work outside this checkout.
