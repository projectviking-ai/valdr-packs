# Task repair suite

Nine cases test whether Task Repairer makes only explicit, authorized repairs
and declines requests it cannot safely apply. Each case starts with fresh task
fixtures in disposable evaluation directories through the installed `valdr` CLI. The suite
uses the same shared runner and `sol-high` profile as workflow authoring.

The public Codex CLI runs the composed Task Repairer persona against a scoped
Valdr MCP broker. Valdr uses the existing `.env` credentials and default license,
with a fresh disposable PM home per case. See the [main guide](../README.md)
for setup, isolation, evidence and agent selection.

```sh
bun evals/run.mjs list task-repair
bun evals/run.mjs doctor task-repair
bun evals/run.mjs run task-repair --profile sol-high \
  --max-repairs 2 --round candidate --dry-run
```

## Cases

| Case | Required behavior |
| --- | --- |
| 01 | Apply an exact checklist-label replacement |
| 02 | Decline a request with no replacement text |
| 03 | Decline conflicting replacements |
| 04 | Apply an exact description replacement |
| 05 | Correct a later item in a second checklist |
| 06 | Apply compatible description and checklist-label edits together |
| 07 | Decline a mixed valid/incomplete request without applying the valid part |
| 08 | Decline an ambiguous duplicate-label target |
| 09 | Decline changes outside description/checklist-label authority |

Use `list task-repair` for full case IDs accepted by `--scenario`. Runs default
to zero repairs; the preview above describes a budget of up to two repair turns
per case.

## What a pass establishes

A successful repair must match the complete expected persisted task, including
every requested edit and all fields that should remain unchanged. Checks also
cover the guard task, metadata, comments/history, filesystem changes, exact
JSON receipt, and the completed read/update/reload sequence.

The broker restricts updates to the exact authorized description and
checklist-label targets. Decline cases permit no mutation attempts: denied,
no-op, reverted, or partial writes remain failures. Request history survives
evaluator repair turns, so a later receipt cannot erase an earlier violation.

Comparisons normalize only metadata row IDs regenerated by the installed CLI
and null optional checklist fields on successful repair cases. Raw before and
after states remain in the evidence. Refusal checks retain the original task
identity and revision.

These fixtures evaluate explicit text repair and boundary handling. They do not
establish whether an agent can infer an unspecified replacement or independently
judge the correctness of the underlying product requirement.
